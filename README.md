# nem-predispatch-bess-advisor

協助儲能（BESS）在澳洲 NEM 的 NSW1 區域做充放電決策與收益評估的兩個靜態網頁，加上一個離線分析層。資料在瀏覽器裡直接取得，不需要伺服器。

各階段的完整規劃、里程碑與業務邏輯見 [`docs/roadmap.md`](docs/roadmap.md)。

## 目的與主線

專案原本想預估已知規格儲能設備在 NSW 市場 15–20 年的收益，後來確認做不到：電池價差一年內大幅壓縮、2029 年 4 月 Eraring 燃煤電廠退場是結構斷點，而新電池上線時程、競爭者報價這兩項最關鍵的資料都沒有真實數據。因此目標改為：

1. **每日決策**：依當下的預調度電價，判斷今天要不要充放電、什麼時候、能賺多少。
2. **中短期收益**：在可信期限內（目前定為至 2029 年 4 月），估計一段期間的收益區間。

兩件事由同一個決策變數串起來：**價差標準**。

> 價差＝放電段均價 − 充電段均價，每段長度＝容量 ÷ 功率。價差達到標準才放電，否則等待。

預調度頁每天**套用**價差標準；情境評估頁定期**檢討**價差標準，並用它預估中長期收益。

## 預調度頁

### 資料來源

| 方式 | 端點 | 何時用 |
|---|---|---|
| 自動讀取 | `POST https://visualisations.aemo.com.au/aemo/apps/api/report/5MIN`，內容 `{"timeScale":["30MIN"]}`，取 `PERIODTYPE = FORECAST` 的列 | 預設。開頁就讀，之後每 5 分鐘一次 |
| 手動上傳 | [NEMWeb PredispatchIS_Reports](https://nemweb.com.au/Reports/Current/PredispatchIS_Reports/) 的 `PUBLIC_PREDISPATCHIS_*.zip` 或解壓後的 CSV | 自動讀取失敗時。上傳後自動更新會暫停 |

自動讀取用的是 AEMO 官網 NEM 資料儀表板背後的 API。它回 `Access-Control-Allow-Origin: *`，網頁可以直接呼叫；NEMWeb 沒有這個標頭，瀏覽器會擋，所以只能手動上傳。這支 API 沒有公開文件，AEMO 改格式時頁面會指出哪一列哪個欄位不符。回應裡也沒有預調度的執行時間。

兩種來源 2026-10-19 實測過：NSW1 都是 67 個 30 分鐘時段，預測到下一個市場日 04:00（NEM 時間）。

### 計算

- 每段長度＝容量 ÷ 功率，連續、滿功率。
- 一個循環是充、放兩段；兩個循環是充、放、充、放四段一起選，取放電段總價減充電段總價最大的組合。每個循環的價差必須為正，且不低於「每循環最低價差」（預設 0）。同分取最早；一個與兩個循環同分取一個；沒有組合符合就不排。
- 來回效率固定 100%，不計損耗。損失係數（MLF）只縮放收益。（階段 1 預計改為：計入效率與損耗）
- 搜尋範圍是整個預測期間，可以跨過午夜。建議計畫一律從空電池開始；「目前電量」只用在自訂價格的試算。

### 階段 1 預計改為

- 讀取 `config/spread_standard.json`，在建議計畫旁顯示「執行」或「等待」；等待時說明目前價差與標準的差距。
- 預估收益計入效率損失、損耗成本與 MLF。
- 頁面說明預調度是預測價、收益包含與不包含的項目、目前價差標準的值與生效日期。
- 自訂價格試算保留，移到主結論下方。

## 情境評估頁

### 目前的資料來源與計算

| 資料 | 來源 | 何時讀 |
|---|---|---|
| 市場預設值 | 程式內的示意價格型態（`src/scenario_presets.js`），不是即時數據 | 開頁 |
| 歷史電價 | 手動上傳 CSV，例如 AEMO 的 `PRICE_AND_DEMAND_YYYYMM_NSW1.csv`；AEMO 網站沒有開放跨網域讀取，網頁無法直接下載 | 上傳時 |
| 特殊日期備註 | 本 repo 標籤為 `special-date`、未關閉的 GitHub issue，以 GitHub REST API 讀取 | 開頁與按「重新整理備註」時 |

- 每日電價＝基準價 × 日型態（清晨小峰、午間再生能源凹陷、傍晚尖峰）＋雜訊，偶發尖峰落在 18 至 21 時。模擬 400 條路徑，亂數種子固定。
- 電池為空時在當日最低的連續四小時充電；之後最高的連續四小時與充電價的價差達標就放電，否則持有，等滿最長天數就強制放電。
- 四小時電池，預設 5 MW／20 MWh；來回效率固定 100%，不計損耗。
- 歷史校準以最小平方法擬合日型態的四個係數，再算尖峰日比例、天氣波動度與四小時價差中位數。檔案含多個區域時用 NSW1。

備註用 issue 表單 [`.github/ISSUE_TEMPLATE/special_date.yml`](.github/ISSUE_TEMPLATE/special_date.yml) 新增。GitHub API 未登入時每個網路每小時 60 次，所以頁面不自動輪詢。issue 內文任何人都能寫，頁面只當純文字顯示。

### 階段 1 預計改為

情境評估頁改為回答三個問題：價差標準要不要調整、這段期間發生了什麼特殊事件、在目前標準下未來一段期間大概能賺多少。

| 項目 | 階段 1 做法 |
|---|---|
| 歷史資料 | 改讀離線分析層輸出的 `data/daily_summary.json`（每日最佳價差與收益），不必上傳 |
| 價差標準檢討 | 選歷史期間，套用目前標準與一組候選標準，比較執行天數與收益，結論為維持、上調或下調 |
| 事件標注 | 改用 `data/special_dates.csv`，經 PR 新增並審查；頁面在圖上標出事件，可切換「含事件日／排除事件日／只看事件日」 |
| 中長期推估 | 選一或多段參考期間，套用價差標準，依目標期間天數換算 P10／P50／P90，並排比較並自動產生說明 |
| 因素現況 | 唯讀顯示 `data/factor_weights.json` 的最近值與月份基準，不直接調整收益 |
| 移除或隱藏 | 七國示意預設、示意參數的蒙地卡羅模擬、新聞事件按鈕、任意 CSV 上傳校準 |

## 離線分析層與因素權重

`data/factor_weights.json` 記錄六個因素對每日套利收益的權重。它由離線分析層 `analysis/` 用 AEMO 歷史資料算出，網頁只讀結果：

| 項目 | 內容 |
|---|---|
| 被解釋變數 | 每天用 `select_best_plan` 與 `config/battery.json` 的設備參數（目前 5 MW／20 MWh、MLF 1）算出的套利收益，取 log(1 + 收益) |
| 因素 | 日均需求、晚間尖峰需求、最小供給餘裕、日均淨進出口、雪梨天然氣事前價、NSW 電池放電功率；氣溫、太陽能與風力、屋頂型太陽能、特殊事件（#14）還沒加入，權重記為 0 |
| 求解 | HiGHS 最小絕對誤差迴歸，權重非負、加總為 1，另外輸出 scale 與截距 |
| 目前擬合品質 | 2024-07-01 至 2026-08-31，共 789 天；R² 約 0.46，平均絕對誤差約 A$2,721／天（收益中位數約 A$2,651／天） |

擬合品質有限，所以階段 1 只把權重當參考，不作為收益預估的依據；接入預估是階段 2 的工作（#12）。

分析層另外輸出 `data/daily_summary.json`（#30）：2024-07-01 起每個交易日的最佳計畫，含各循環的充放電開始時間、均價、價差與淨收益，以及被排除的日子與原因。計畫與權重用同一套選窗規則與 `config/battery.json`，計入效率與損耗。情境評估頁的價差標準檢討（#32）、參考期間推估（#33）與事件標注（#31）以它為資料來源。

模型、欄位與每個來源的細節在 [`docs/data_sources.md`](docs/data_sources.md)。原始資料約 1.9 GB，不在 repo 裡；重新產生要在 repo 根目錄執行（兩份 JSON 每月一起更新）：

```bash
NEM_INPUT_DIRECTORY=<原始資料目錄> uv run python -m analysis.build_factor_weights
NEM_INPUT_DIRECTORY=<原始資料目錄> uv run python -m analysis.build_daily_summary
```

改了 `analysis/` 的程式或 `config/battery.json` 卻沒重新產生兩份 JSON（權重另外檢查 `data/external/`），CI 的 `analysis` job 會失敗。指紋涵蓋 `analysis/` 第一層的每個 `.py`，所以只改其中一個模組，兩份 JSON 也都要重跑。

## 本機執行

頁面用 ES module 載入 `src/`，要經過 HTTP 才開得起來，直接開 HTML 檔案不行：

```bash
uv run --no-project python -m http.server 8000
```

然後開 <http://127.0.0.1:8000>（預調度頁）或 <http://127.0.0.1:8000/scenario/>（情境評估頁）。

## 測試

需要 Node 22 以上，沒有 npm 依賴：

```bash
node --test "tests/*.test.js"
```

離線分析層（`analysis/`，Python）用 uv 管理，測試用 pytest：

```bash
uv sync
uv run pytest
```

`analysis` 沒有打包成可安裝的套件（`pyproject.toml` 沒有 build-system，`uv sync` 只裝依賴），所以 Python 指令一律在 repo 根目錄執行，模組用 `uv run python -m analysis.<模組名>` 啟動；在別的目錄執行會出現 `ModuleNotFoundError: No module named 'analysis'`。pytest 由 `pyproject.toml` 的 `pythonpath = ["."]` 處理。

CI 在每個 PR 跑這兩組測試（`.github/workflows/ci.yml` 的 `test` 與 `analysis` 兩個 job）。
